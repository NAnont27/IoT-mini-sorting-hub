# แผนเริ่มงาน HW/System บนโต๊ะ — Mini Sorting Hub

วันที่ 11 พฤศจิกายน 2026

อ้างอิงหลัก: [เอกสารโปรเจกต์ฉบับรวม](PROJECT_BRIEF_TH.md)
ส่งต่อ AI: [Prompt ทีม AI](../ai/AI_TEAM_HANDOFF_PROMPT_TH.md)

สถานะ: เป็นแผน ยังไม่ได้ต่อวงจร เขียน firmware ติดตั้งบริการ หรือทดสอบจริงในรอบนี้ ผู้ใช้ยืนยันว่าอุปกรณ์ครบตามรายการเดิม รวม VL53L0X และ AS5600 ยังไม่มีการเปลี่ยนรุ่น

อัปเดตบอร์ดจากภาพผู้ใช้: ESP32-S3-N16R8 ใช้ขาที่พิมพ์ 4 (GPIO4) สำหรับ HX711 DT และ 5 (GPIO5) สำหรับ HX711 SCK ในการทดสอบขั้น 2 ไม่ใช้ผัง GPIO32/33 ของ ESP32 รุ่นปกติ ผลการทดสอบ HX711 ยังไม่ยืนยัน

## 1. เป้าหมายรอบนี้

ทดสอบอุปกรณ์แยกชิ้น จากนั้นเชื่อมข้อมูลให้วิ่งครบหนึ่ง job บนโต๊ะ ยังไม่ประกอบโครงถาวร ไม่ต้องทำสายพาน/รางจริง ไม่ถือว่าผลจำลองเป็นหลักฐานคัดกล่องทางกลจริง

ลำดับ: น้ำหนักนิ่ง → job_id → ถ่ายภาพ/OCR/AI/resolver → POSITION → ตรวจมุม → RELEASE → จำลองผ่าน IR → บันทึกผล/เว็บ

## 2. เจ้าของงานสามคน

| คน | งานหลัก | ชิ้นส่งมอบ |
|---|---|---|
| H1: Sensor node | ESP32, HX711/load cell, VL53L0X, IR สี่ตัว, MQTT telemetry | โปรแกรมทดสอบรายชิ้น + firmware อ่านเซนเซอร์ |
| H2: Actuation/Gateway | Servo สองตัว, ไฟ/ปุ่ม, AS5600 และ BH1750 บน Pi | โมดูล actuator สำหรับรวม firmware กับ H1 + Pi sensor service + ผังไฟ |
| H3: System | Mosquitto, Backend/state machine, InfluxDB, job store, API/เว็บ | รับข้อมูล สั่งงาน เก็บ/ค้นประวัติ และเว็บพื้นฐาน |

H1 กับ H2 ใช้ ESP32 ตัวเดียว จึงทำโมดูลแยกและนัดสลับทดสอบ ไม่แก้ main firmware/ผังขาคนละชุด H1 เป็นผู้รวม firmware; H3 เป็นผู้รวมบริการ Pi และ Backend ผู้ทำ AI คนที่ 3 ช่วย Dashboard ได้เมื่อ resolver พร้อม

## 3. ข้อกำหนดร่วมก่อนต่อไฟ

- Pi เป็น Gateway อ่าน AS5600 และ BH1750 โดยตรงผ่าน I2C; Node อ่านน้ำหนัก/ToF/IR ยังคง 5 ชนิด Node 3 และ Gateway 2
- Servo MG90S และ MG996R ใช้ Adapter 5V 5A แยก ต่อ GND ร่วมกับ ESP32 แต่ไม่เอาสาย +5V จากแหล่งจ่ายหลายตัวผูกขนานกัน
- Pi ใช้แหล่งจ่ายของ Pi; ESP32 เริ่มจาก USB อย่าส่งไฟ Servo ผ่านขาบอร์ด/เบรดบอร์ด
- Adapter P0384 หัว 5.5×2.5 มม.; ตรวจขั้วและวัดเอาต์พุตจริงก่อนต่อ
- ตรวจโมดูลและ logic level ของล็อตที่ได้ โดยเฉพาะ E18-D80NK ห้ามนำ output 5V เข้า ESP32/Pi
- I2C ฝั่ง Pi ต้องไม่มี pull-up ไป 5V ตรวจโมดูลก่อนแชร์บัส
- Servo ทดลองช่วงกลาง/ช่วงแคบก่อน ไม่กวาดชนปลายหรือถือว่าองศาที่สั่งเท่ากับมุมจริง
- AS5600 ต้องมีแม่เหล็ก Diametric ตรงแกน; เริ่มหมุนด้วยมือก่อน
- Load cell ต้องทำฐานทดสอบและจุดรับแรงถูกต้อง ไม่วางเซนเซอร์หลวมแล้วใช้ค่าเป็นผลสอบเทียบ
- ยังไม่ล็อก GPIO จนตรวจรุ่น ESP32/ชื่อขาบนบอร์ดจริง; ใช้ config เดียวและจดสายทุกเส้น

## 4. MQTT และที่เก็บข้อมูล

ใช้หัวข้อตามเอกสารหลัก ไม่ใช้ชุดชื่อ sorter/sensor/* ที่เคยยกตัวอย่างในแชต เพื่อไม่ให้สองฝั่งคนละ interface

| Topic | เจ้าของข้อมูล |
|---|---|
| sorter/weight | ESP32: น้ำหนัก/ความนิ่ง/คุณภาพค่า |
| sorter/height | ESP32: ระยะ/ความสูงเฉพาะจุด/สถานะค่า |
| sorter/passage | ESP32: tray_exit, A, B, HOLD และเหตุการณ์ขอบสัญญาณ |
| sorter/gateway | Pi service: มุม/สถานะแม่เหล็ก และแสง พร้อมความสดของแต่ละค่า |
| sorter/vision | Backend: ผลโมดูล AI |
| sorter/cmd | Backend → ESP32: คำสั่งที่ state อนุญาต |
| sorter/ack | ESP32: รับ/ปฏิเสธ/จบคำสั่ง พร้อม command_id |
| sorter/actuator | ESP32: สถานะกลไก/fault |
| sorter/status | heartbeat ของแต่ละ device_id |

คงชื่อฟิลด์ schema_version, device_id, session_id, seq, uptime_ms ตามเอกสารหลัก ข้อมูลต่อเนื่องก่อนมี job ใช้ job_id=null; Backend ผูกข้อมูลเข้ารอบปัจจุบันและบันทึกช่วงเวลา ไม่ให้ Node สร้าง job_id แข่ง Backend

ผล AI ใช้ resolved_room, resolved_floor, target_bin, reason_code เหมือนเอกสารหลัก Envelope outcome เป็นข้อเสนอใน prompt ส่งต่อ ให้ล็อกก่อนรวมงาน

ใช้ command_id ป้องกันคำสั่งซ้ำภายใน job; ไม่ retain คำสั่งเคลื่อนกลไก ตรวจ session/อายุคำสั่งก่อนทำงาน ไม่ถือว่า ACK รับคำสั่งเท่ากับคัดสำเร็จ

เมื่อ Pi อ่านมุมตรงเป้าหมายและสดพอ Backend จึงอนุญาต RELEASE; ESP32 ต้องตรวจ active job/คำสั่งและสถานะท้องถิ่นด้วย Node ไม่ได้อ่าน AS5600 เอง จึงห้ามอ้างว่าตรวจมุมเองโดยไม่มีผลจาก Pi

| ที่เก็บ | หน้าที่ |
|---|---|
| InfluxDB | telemetry และเหตุการณ์สถานะตามเวลา ต้อง query ย้อนหลังจริง |
| SQLite ใน Pi (ข้อเสนอเลือกจาก JSON/SQLite ในเอกสารหลัก) | job record, result, reason, image path และข้อมูลสำหรับค้น |
| ไฟล์ใน Pi | ภาพต้นฉบับ/ภาพ OCR/ข้อความ/CSV ที่ยืนยันแล้ว |

job_id เป็นคีย์งาน tracking_id ว่างหรือซ้ำข้าม job ได้ตามขอบเขตเดิม ไม่สร้างเงื่อนไข unique tracking_id

## 5. ลำดับทำงานและเกณฑ์ผ่าน

| ขั้น | ทำอะไร | ต้องเห็นก่อนขยับขั้น |
|---|---|---|
| B0 ตรวจของ/ไฟ/ขา | จดรุ่น ผังขา แหล่งจ่าย ตรวจแรงดัน | มี wiring checklist เดียว ไม่มี GPIO รับสัญญาณเกินพิกัด |
| B1 อ่านแยกชิ้น | โปรแกรมทดสอบอุปกรณ์ทั้งหมดรวมกล้องของทีม AI | แต่ละชิ้นมี log/ผลจริง แยก bad reading จากค่าศูนย์ |
| B2 เส้นข้อมูลแรก | ESP32 weight → MQTT → Backend → InfluxDB → เว็บ | เห็นค่าสดและ query ย้อนหลังได้หลัง restart หน้าเว็บ |
| B3 เส้นคำสั่งกลับ | ปุ่มทดสอบบนเว็บ → Backend → cmd → Servo → ack | ขยับได้ในช่วงทดสอบ ส่งคำสั่งเดิมซ้ำแล้วไม่ทำซ้ำ |
| B4 รวม telemetry | เพิ่ม ToF, IR×4, AS5600, BH1750, ปุ่ม/ไฟ | ระบุแหล่งข้อมูลถูกและตรวจ offline/stale ได้ |
| B5 รอบจำลอง | ใช้ AI fixture สั่ง A/B/HOLD, หมุนแม่เหล็กด้วยมือเข้าเป้า, บัง IR | เดินสถานะครบและเก็บผล แสดง SIMULATED/PASSAGE_SIMULATED ชัด |
| B6 รอบ AI จริง | ภาพจาก Camera 3 → OCR/Gemini/resolver → รอบจำลองทางกล | job_id เดียวตลอด มีภาพ/ผล/เวลา/เหตุผล คัดตามผลจริง |
| B7 แกนทดลอง | ติด Servo/AS5600 กับแกนรางทดลองที่รองรับแยก | มุมที่อ่านสัมพันธ์กับแกนจริง สอบเทียบ A/B/HOLD; ยังไม่ประกาศคัดกล่องจริงสำเร็จ |

เริ่ม B5 ได้ก่อน B7 แต่ต้องประกาศชัดว่ามุมถูกหมุนจำลองด้วยมือ ไม่ใช่ Servo มี feedback จริง ห้ามข้าม interlock โดยใช้มุมสั่งแทนมุมวัดในโหมดจริง

## 6. การจำลองและสถานะผิดพลาด

- demo_mode ต้องเปิดอย่างชัดเจน บันทึกใน job/หน้าเว็บ แยก sensor จริงกับ mock
- RELEASE เป็นการขยับ Servo บนโต๊ะ กล่องยังไม่ไหลจริง ใช้กล่อง/มือผ่าน IR ตามลำดับ
- สำเร็จเมื่อ tray_exit และ IR ช่องเป้าหมายเกิดตามลำดับ/เวลาที่กำหนด ไม่ใช่รอ sleep แล้วเพิ่มตัวนับ
- มุมไม่ถึง/ค่าแม่เหล็กใช้ไม่ได้/ข้อมูลมุมเก่า → ไม่ RELEASE และแจ้ง fault
- ผิดช่อง/ไม่ถึงช่อง → MISROUTE/FAULT ไม่เพิ่มตัวนับสำเร็จ
- AI SERVICE_ERROR → PAUSED_AI ค้าง job และรอกดลองใหม่ ไม่เปลี่ยนเป็น HOLD
- OCR ข้อมูลจำเป็นไม่พอ → ถ่ายซ้ำแบบมีขอบเขต แล้ว HOLD ตามกฎ
- หยุดรับงานใหม่เมื่อพัก กล่องปล่อยแล้วคงรางเดิมจนจบหรือ fault
- คำสั่งจากรอบเก่า/ซ้ำ/หลัง reconnect ต้องไม่ทำให้เปิดประตูเอง
- thresholds/timeouts เริ่มเป็น config สำหรับ bench แล้วสอบเทียบใหม่กับกลไกจริง ไม่อ้างเป็นพิกัดรับกล่องจริง

## 7. เว็บขั้นต่ำและงานที่พักไว้

หน้าแรกแสดง state, online/stale, ค่าสด, active job, ภาพ/ผล AI, เป้าหมายกับผลจริง, reason และ demo mode

มีปุ่มพัก/เริ่มต่อ, retry AI, ยืนยันหลังเคลียร์ fault และส่วนค้นประวัติ/กราฟจากฐานข้อมูลจริง ปุ่มทดลอง actuator จำกัด bench/test mode ไม่ปรากฏเป็นการสั่งข้าม interlock ของ production flow

ทำ CSV upload/preview และค่าชั้นคั่นตามขอบเขตก่อนรอบเดโมเต็ม ไม่สร้างหน้าแก้ผู้พักทีละคน ไม่ทำปิดเคส HOLD หรือ business dedup เลขพัสดุซ้ำ

## 8. แผนตามเวลาที่เหลือ

เป็นเป้าหมาย ไม่ใช่รายงานงานเสร็จแล้ว หากขั้นก่อนไม่ผ่านให้แก้และปรับแผน ไม่เร่งต่อกลไกเพื่อให้ตรงวันที่

- 11–13 พ.ย.: ส่ง AI prompt, ล็อก interface, B0–B2 และเริ่ม B3 ตามความพร้อม
- 14–19 พ.ย.: หยุดงาน ไม่มี dependency บังคับหรือเดดไลน์ให้ทีมทำในช่วงนี้
- 20–22 พ.ย.: B3–B5 รวมข้อมูลและรอบจำลอง
- 23–25 พ.ย.: B6–B7, เตรียมกล่องจริงสามขนาดและออกแบบกลไกจากผล bench
- 26 พ.ย.–2 ธ.ค.: ประกอบกลไกจริง สอบเทียบและทดสอบคัดกล่องจริง รวม fault cases
- 3–7 ธ.ค.: เก็บผลตาม Criteria, fps/accuracy/latency, สไลด์/วิดีโอและตรวจส่ง; ไม่เพิ่มฟีเจอร์ใหม่

## 9. เริ่มรอบถัดไป

1. ตรวจรุ่น ESP32/ชื่อ GPIO ที่พิมพ์บนบอร์ด และอุปกรณ์แปลงระดับที่มี
2. ทำผังไฟและ pin map แบบตรวจสอบได้ก่อนต่อ
3. ตั้งโครงโปรเจกต์ firmware/gateway/backend/ai-contract/tests/docs โดยไม่สร้าง AI pipeline ซ้ำกับทีม AI
4. เริ่มจาก ESP32 อ่าน HX711 แยกชิ้น พร้อม Pi ติดตั้ง Broker/Backend สำหรับเส้นข้อมูลแรก

แผนนี้ยังไม่ระบุเวอร์ชันแพ็กเกจ คำสั่งติดตั้งหรือผังขาเฉพาะรุ่น ก่อนลงมือให้ตรวจ environment/เอกสารทางการที่ตรงอุปกรณ์จริง ไม่เดาขา ESP32 จากชื่อทั่วไป
